# Baseline de performance — 2026-10-19 (BF-003)

Primeira medição controlada do MariPDF com o medidor embutido
(`MARIPDF_BENCH`, BF-002) sobre o corpus sintético versionado (BF-001).

| Item | Valor |
|---|---|

| GPU | NVIDIA GeForce RTX 3080, driver 32.0.16.1742 |
| RAM | 128 GB |
| Disco | SSD |
| SO | Windows 11 Pro, build 26200, 3 monitores, escala 125% |
| Build | `cargo build --release`, commit `0c921b4`, rustc 1.93.1 |
| Binário | 20,9 MB (`panic = "unwind"`, PDFium embutido) |

## Método

- Corpus: `python tools/make_corpus.py bench/corpus --manifest bench/corpus.toml`,
  que gera 10 PDFs determinísticos (hashes no manifesto).
- Execução: `pwsh tools/bench.ps1 -Runs 3`, com estado isolado em
  `MARIPDF_DATA_DIR`. A coluna "frio" é a 1ª rodada; as demais colunas são a
  mediana das rodadas 2 e 3.
- Roteiro do medidor, por PDF:
  1. abrir e apresentar a página 1;
  2. salto distante sem cache (meio do documento);
  3. página vizinha, já prefetchada;
  4. zoom 160%;
  5. busca por "MariPDF";
  6. 40 saltos no modo contínuo.
- O tempo de frame é o custo de CPU do `update` da UI. Não inclui a
  apresentação na GPU.
- Working set e pico vêm de `K32GetProcessMemoryInfo` ao fim do roteiro.

## Achado: backend gráfico

A primeira rodada usava o backend padrão do wgpu (Vulkan nesta máquina). Com o
`text-100.pdf`:

| Backend | Working set | 1º frame |
|---|---|---|
| Vulkan (padrão anterior) | 345 MB | 702 ms |
| **DX12 (novo padrão)** | **200 MB** | **499 ms** |
| GL | 180 MB | 382 ms |

O app passou a preferir DX12, com GL de reserva e GPU de baixo consumo
(`main.rs`, `wgpu_configuration`). Em todo o corpus, isso reduziu cerca de
95 MB de working set e 90 ms até o primeiro frame. `WGPU_BACKEND` continua
sobrescrevendo para diagnóstico.

## Próximos alvos

   PDFium, e reduzir o que for nosso.
3. **Scan com prefetch (67 ms):** é decodificação de JPEG grande; candidato a
